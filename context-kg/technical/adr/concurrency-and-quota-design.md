# Lyra 做题并发与 APIGO 配额调度设计

## 决策与依据

状态：设计提案，尚未实现新调度器。用户给定 RPM 1,000、TPM 2,000,000；额度作用域、时间窗口、是否另有服务端并发上限仍需接口确认，不能推断每个模型独占一份额度。

采用全局题目队列和统一请求准入。所有共用同一 Key/Workspace 的模型、effort、模拟器和 Judge 聚合计算配额。建议目标 RPM 800、TPM 1,600,000，保留 20% 余量；同工作区还有其他业务时，需要额外扣除它们的用量。模型请求并发从 16 起步，32 为第一轮调优上限，不立即按 1,000 RPM 启动大量容器。

当前代码按全局 8 个 episode、单运行默认 4 个 episode、每作业 2 题、同时 2 个作业控制，未实现跨 relay 的 RPM/TPM 协调。题目在整个 Agent 和评分阶段持有槽位，存在重评分任务挤占轻任务的问题。一个 episode 可能有多个串行请求，τ² 还包含模拟器和 Judge；episode 数不等于请求并发，更不等于 RPM。

## 请求并发估算

令 T 为每次 API 请求平均计入 TPM 的 token，L 为平均请求占用时长（秒）。稳态吞吐估算：

`目标请求数/秒 = min(800/60, 1600000/(60*T))`

`所需请求并发 ≈ 目标请求数/秒 × L`

| T | L | 80% 配额对应的请求并发 | 主要约束 |
|---:|---:|---:|---|
| 10,000 | 30 秒 | 80 | TPM |
| 20,000 | 60 秒 | 80 | TPM |
| 50,000 | 60 秒 | 32 | TPM |
| 100,000 | 60 秒 | 16 | TPM |

这些是计算示例，不是本项目实测。持续并发 32、平均请求 60 秒时，每分钟约 32 次请求；平均每次 50,000 token 恰好消耗 1,600,000 TPM。请求变快、输入变长都会改变可承受并发，所以固定 32 不是保证。高 effort 的耗时和 token 都可能增大，方向相反，不应机械按 effort 倍增或减半。

## 三类资源分别控制

1. Episode 槽位：轻任务候选上限 16–32；τ² 初始 4；SWE 初始 2。全部受实测宿主资源总量限制，不能把这些数直接相加作为无条件启动数。当前全局 8 槽需改造后才能突破。
2. API 请求槽位：统一配额服务管理，初始 16，上限 32；后续有证据再升到 48/64。已拿 episode 槽的 Agent 仍必须在每次请求处申请配额。请求槽从实际发送持有到流关闭/终态，不在首 token 时释放。
3. 环境准备与评分槽位：SWE 镜像准备 1，SWE 评分初始 1–2，LCB 评分初始 2–4，均受 CPU、内存、PID 和磁盘限制。评分阶段释放模型执行槽，题目仅在评分完成后记作完成。

资源准入以容器组计算：普通 episode 含 Agent 与 relay；τ² 额外有 Gym 和 simulator relay；SWE 额外有官方工具环境。SWE 单题官方环境配置 4 GB，不能把 32 API 请求并发解释成 32 个 SWE 容器组。实际内存预算另留系统余量，缺资源的任务保持队列态。

## 调度架构

`持久化题目队列 → 公平派发 → Agent/环境 → 每次请求统一准入 → APIGO → 独立评分队列 → 结果`

- 全量计划支持各评测集独立题数或 all，不再共享 sample_size；预展开 case ID 与实验变体但不一次创建所有协程/容器。
- 按 benchmark × variant × trial 轮转公平派发；老任务提高优先级，SWE 长任务不能占尽槽位。低并发任务完成后，空闲容量可被其他队列使用。
- relay 向可信控制器请求准入；控制器自行从冻结配置确定 Key/Workspace/预算身份，Agent 不能指定配额桶。相同 Key 的多个模型连接通过服务端不可逆标识归组，密钥不出现在事件/导出中。
- 所有适用配额桶必须同时满足：Workspace、API Key、已证实的模型/供应商限制，以及本地资源与美元预算。不能按连接数复制额度，不能通过换 Key 绕过 Workspace 上限。
- 本地单控制器用持久化队列和原子事务即可；先不引入 Redis。未来多控制器才需共享配额与 lease 存储。

## 配额和费用的区别

每次请求预留一次 RPM 和预计 TPM；TPM 预留包含上下文与输出预测，算法版本冻结，结合模型 tokenizer 与近期 P95 用量并依据 APIGO 实际准入口径校准。美元预算继续使用独立、可信的费用上限预留，不能用平均 token 预测保证不超支。

配额窗口内的未知请求保守保留，过窗后释放速率预留；费用未知则持续保留美元预留直到对账。已到达上游但响应丢失的请求，不因客户端超时退回全部费用。流最终 usage 完成后校准本地速率统计；输入、输出、缓存、reasoning 分开保存，避免重复计数。

默认请求节流避免分钟切换突发。若服务端提供窗口、重置时间、remaining，则按其语义实现；缺少信息采用保守滚动窗口与平滑发送。本地估计不是平台剩余额度，Console 标注来源和新鲜度。

## APIGO 已核对的接口边界

当前本地 Gateway 源码支持 API Key 和 Workspace 级 RPM、TPM、concurrency。推理请求携带 `x-gateway-quota-probe: 1` 且工作区开启 `quota_probe_enabled` 时，可输出：

- `x-tidemind-quota-apikey-rpm-limit`
- `x-tidemind-quota-apikey-tpm-limit`
- `x-tidemind-quota-apikey-concurrency-limit`
- 对应的 `x-tidemind-quota-workspace-*` 三个字段。

这批头是配置上限，不是完整的实时 remaining/reset。probe 开关受服务端控制；`/v1/models` 提前返回，不提供这些 quota probe 头。429 响应有 `Retry-After`，错误原因可区分 Key/Workspace 与 RPM/TPM/concurrency。不能为获取配额发送额外付费探针，在授权的正常请求上收集即可。现有 relay 需增加这些字段的白名单持久化，当前尚未接入。

建议 APIGO 后续提供模型 Key 可读、仅限自身的配额快照接口（新接口提案，不是已存在能力）：返回作用域、限额、窗口、remaining/reserved、reset_at、observed_at、计量口径。平台历史 usage 接口可以用于观测，不等同于当前可用额度。接口缺失时使用用户确认的上限和本地统计，UI 显示“剩余额度未知”。

代码依据（相邻 ai-gateway 仓库）：`gateway/src/gateway/engine.rs`、`gateway/src/gateway/admission.rs`、`gateway/src/quota/manager.rs`；本仓库 `src/vohu_evals/console/live_scheduler.py`。

## 自适应、失败与恢复

以 16 请求并发启动；每档至少观察 3–5 分钟并取得足够完整请求样本，短窗口不稳定时延长。无 429、用量低于目标且请求有排队、宿主资源充足时，每档增加 4，到 32 后复核再决定更高上限。达到 TPM 目标即停止提升；增加并发不保证增加有效吞吐。

遇到 429，尊重 Retry-After，暂停受影响共享桶，带随机抖动恢复；没有明确原因时保守降低该作用域并发，例如乘 0.7。不自动降低 effort、裁剪上下文或改变题目预算来制造吞吐提升。

统一记录 attempt。明确未发送或服务端拒绝的请求可按有限次数重试；超时且可能已执行的推理不盲目重放。尤其 τ² 的工具状态不能重放整个 episode；恢复需要官方环境 checkpoint 支持，否则保留系统失败。控制器重启不自动重复付费请求，按 lease 和请求证据恢复；旧进程必须先停止再回收并发槽。

## Console 和实验公平性

新增并发面板：活跃 episode、API in-flight、评分任务、排队数、RPM/TPM 实测值与上限、429、重试、CPU/内存、当前瓶颈。每个额度显示来源（用户配置/响应头/平台快照）、作用域、观测时间。

计时分为排队等待、配额等待、容器准备、Agent、API/首 token、评分、总墙钟。同时保留用户实际等待和剔除本地队列后的执行耗时，不把请求准入等待悄悄删掉。ETA 按各 benchmark/model/effort 的试跑分布及资源瓶颈估算，显示区间。

吞吐模式允许自适应并发；正式时延对比模式固定并发与负载、交错调度变体，并记录限流/等待条件。不能在不同负载下把高并发吞吐差异直接归因于模型速度。质量与成本比较仍冻结 harness、effort、工具、题集和预算。

## 落地顺序与验收

1. 配额响应采集、请求用量观测和等待时间字段；不改变调用量。
2. 跨 relay 的统一请求准入、共享 Key/Workspace 配额与原子预算；假时钟测试 RPM/TPM 窗口、多桶竞争、取消、未知用量、429、重启不重放。
3. 全局题目队列、资源感知公平派发、评分解耦与各题集 all；验证长任务不饿死短任务，模拟器费用和配额不漏计。
4. Console 并发面板与自适应控制；在已有授权预算内通过真实小样本校准，扩大量前另行确认费用。用户给出的速率上限不等于授权新增评测支出。
